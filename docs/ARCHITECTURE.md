# Архитектура Questy 2.0 — этап 1

## Цель

Безопасно разделить монолит `index.html` на статические файлы, обновить навигацию и оставить существующие данные совместимыми. Не пытаться в рамках первого этапа одновременно переписать все игровые механики.

## Последовательность загрузки

`core.js` → `content.js` → `state.js` → `migrations.js` → `mining.js` → `ui.js` → `daily.js` → `goals-achievements.js` → `calendar-shop.js` → `bootstrap.js`.

Это **не ES modules**: все файлы используют общее глобальное лексическое пространство из исходного скрипта, загружаются обычными тегами `script` без `async`/`defer`. Важно соблюдать порядок. Явное разделение зависимостей — отдельная будущая задача.

## Навигация

Нижние вкладки: `task`, `adventures`, `calendar`, `shop`, `profile`.

Добыча — служебный экран `mining`, открываемый кнопкой на главной. Когда добыча видима, нижняя вкладка «Главная» остаётся активной. Возврат закрывает добычу.

## Хранение и миграция

Текущая версия сохраняет исторические ключи `balance`, `streak`, `mining`, `owned_themes`, `owned_frames`, `history` и дневные ключи `state_YYYY-MM-DD`, `rerolls_YYYY-MM-DD`, `unlocks_YYYY-MM-DD`. Локальный кеш использует префикс `g_`; VK Storage — исходные имена без префикса.

`migrateLegacyStorage()` запускается до `loadProgressFromLocal()`. Для каждого ключа она копирует значение из старого локального имени в `g_<key>`, **только если `g_<key>` отсутствует**. Она не удаляет старые ключи, не изменяет VK Storage и не перезаписывает существующие значения.

`questy_schema_version=2` — локальный диагностический маркер, не номер серверной миграции.

### Известные ограничения

- Пока нет серверного авторитетного учёта Q и платных прав на контент.
- Использование VK Storage вместе с резервной локальной копией требует тестирования конфликтов нескольких устройств.
- Нет облачной миграции форматов данных, потому что текущий этап **не меняет формат старых записей**.
- Долгосрочно нужно перенести игровые модули на явные импорты и изолировать чтение/запись данных.
- Очередь сохранения текущей версии не гарантирует атомарность игровых транзакций; перед введением платных пропусков это нужно решить.
